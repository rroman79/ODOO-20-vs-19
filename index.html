Ліцензійна пастка ролі «Light User» (~€8/міс)

У версії Odoo 20 запроваджено підтип користувача Light User із вартістю близько €8/міс (проти ~€20/міс за Standard User). Проте присутній критичний підводний камінь у логіці підрахунку.

Ризик: Автоматична тарифікація HR

Кожен створиний запис у картці працівника (hr.employee) — навіть якщо працівник це фасувальник або водій без доступів до веб-інтерфейсу (без системного залогінювання) — автоматично враховується як Light User.

Приклад: На підприємстві «Вареники від Бабусі» працює 200 робітників цеху. Якщо їх завести у module Employee для обліку змін, Odoo дорахує 200 × €8 = €1,600/міс (€19,200/рік) незапланованих витрат.

Тригер каскадного підвищення до Full User

Якщо користувачу Light призначити хоча б одну розширену групу прав (наприклад, видати права «Approver» у погодженні відпусток чи доступ до перегляду базового складу), система мовчки конвертує статус користувача у Full User (€20/міс).

  • Перевіряйте групи res.groups перед призначенням ролей.
  • Використовуйте кастомні моделі для працівників без логіну, якщо не потрібен HR-модуль.

Інфраструктурний стрибок: Python 3.12+ & PostgreSQL 16+

Odoo 20 припиняє підтримку Python 3.10 та PostgreSQL <15. Для On-Premise та розгортань Odoo.sh це вимагає повної модернізації серверного стеку.

Ubuntu OS Migration Перехід з 22.04 LTS на 24.04 LTS

Оновлення ОС та збірка системних залежностей (pgvector, libpq-dev, pillow). Простій системи: 2-4 години.

PostgreSQL 16 Partitioning Прискорення SQL-запитів

Використання покращеного партиціонування таблиць `stock_move_line` та `account_move_line` дає до +35% швидкості у звітах ERP.

Перемикач «Tax Excl. / Tax Incl.» (`document_tax_mode`)

B2B & B2C Harmony

Раніше для роботи з B2B (ціни без ПДВ) та B2C (ціни з ПДВ) вимагалося створення подвійних прайс-листів або складних податкових позицій (Fiscal Positions). В Odoo 20 на рівні документа додано поле document_tax_mode.

1. B2B Продажі

Перемикач у режимі Excl. Автоматично додає 20% ПДВ поверх базової гуртової ціни вареників.

2. B2C Фірмові магазини

Перемикач у режимі Incl. ПДВ вираховується з кінцевої роздрібної ціни на касі POS.

3. Економія на кастомізації

Усуває потребу в сторонніх модулях перерахунку податків для комбінованих мереж.

Революція Безпеки: Об'єднання в модель `ir.access`

Застарілий розподіл між правами на модель (ir.model.access) та правилами записів (ir.rule) ліквідовано. Меню "Record Rules" видалено з інтерфейсу налаштувань.

Як було (Odoo 19 та раніше):

  • CSV файли ir.model.access.csv для CRUD прав.
  • XML файли для прав на рівні рядків (Domain rules).
  • Складність налагодження конфліктів у логіці OR/AND.

Як стало в Odoo 20 (`ir.access`):

  • Єдина уніфікована матриця доступу в інтерфейсі.
  • Домени записів визначаються безпосередньо в конфігурації ролі.
  • Швидкість обчислення SQL-запитів зросла на ~20% завдяки відсутності подвійного JOIN `ir_rule`.

Трансформація Контактів: Видалення перемикача типу «Person/Company»

[вторинне] Ризик для ФОП

У картці контакту більше немає ручного вибору «Фізична особа / Компанія» через перемикач. Прапорець is_company тепер є **computed пропонованим значенням**, яке обчислюється автоматично на основі заповнення Tax ID (vat) або структури зв'язаних контактів.

⚠️ Критичний підводний камінь для України (ФОП та контрагенти без ЄДРПОУ):

Під час міграції бази «Вареники від Бабусі» контрагенти-ФОП, у яких у полі VAT (ІПН) був занесений 10-значний номер або поле було порожнім, можуть автоматично визначитися як **Person**, а не **Company**. Це призводить до:

  • Втрати відображення назви компанії у первинних документах (видаткових накладних).
  • Помилок формування ПДВ-податкових накладних при інтеграції з M.E.Doc / Вчасно.

Революція на Складі: Нова структура руху товарів

1. Scrap модель видалена

Окремий документ stock.scrap видалено. Списання браку замороженого тіста або зіпсованої сировини виконується через звичайний stock.move з прапорцем is_scrap=True.

2. Спрощені повернення

Кнопка «Повернути» збереглася. Проте усунуто обов'язкову прив'язку до складного модального вікна (Wizard). Створювати повернення від покупця (B2B точки) тепер можна як кнопкою з відвантаження, так і прямим документом руху.

3. Перемикач `store_by`

Замість прапорців `use_product_lots` / `use_production_lots` введено єдине нове поле **`store_by`** зі значеннями:
quantity, lot, serial, untracked.

4. Native Wave & Batch

Групове відбірання (Batch Pick) та Хвильове (Wave Pick) перенесені в ядро модуля складу. Впроваджено AI-рекомендатор min/max залишків у правилах дозамовлення.

Виробництво: Continuous Production vs Ризик скасування Strict Consumption

Continuous Production (Покрокове оприбуткування)

Як працює: Готова продукція оприбутковується на склад частинами безпосередньо в процесі виготовлення, не чекаючи завершення всієї зміни або закриття виробничого замовлення (MO).

🚀 Бізнес-перевага: Першу готову партію (наприклад, 100 кг вареників) можна одразу продавати та відвантажувати в машину доставки, поки цех продовжує ліпити решту 9,900 кг з Замовлення на виробництво 1 тонни.

Ризик: Усі MO стали Flexible!

У Odoo 20 видалено параметр Strict Consumption. Усі виробничі замовлення за замовчуванням дозволяють списувати більше або менше сировини (фаршу/борошна), ніж вказано у специфікації BOM.

Рішення для БА: Для збереження рецептури «Вареників від Бабусі» необхідно налаштовувати Automated Validation Rules або розробляти застережні Python-констрейнти.

Поетапне виведення з експлуатації XML-RPC / JSON-RPC -> Перехід на JSON-2 API

BREAKING CHANGE

У Odoo 20 повністю видалено сервіс `/xmlrpc/2/db`. Інші ендпоінти XML-RPC оголошено застарілими (deprecated) з повним вилученням у Odoo 22.0. Усі нові інтеграції (з ТЗД, вагами, роздрібними терміналами, BAS/1C) зобов'язані переходити на JSON-2 API (`POST /json/2/`).

Новий формат запиту: JSON-2 API (Python Client) 
import requests

# Ендпоінт Odoo 20 JSON-2 API
URL = "https://varenyky.odoo.com/json/2/api"

headers = {
    "Content-Type": "application/json",
    "X-Odoo-Api-Key": "your_generated_api_key_here"
}

# Отримання залишків замороженої продукції
payload = {
    "jsonrpc": "2.0",
    "method": "call",
    "params": {
        "model": "stock.quant",
        "method": "search_read",
        "args": [[["location_id.usage", "=", "internal"], ["quantity", ">", 0]]],
        "kwargs": {
            "fields": ["product_id", "quantity", "lot_id", "location_id"],
            "limit": 50
        }
    },
    "id": 1
}

response = requests.post(URL, json=payload, headers=headers)
print(response.json())

Списання браку в Odoo 20 (Python)

Створення `stock.move` з прапорцем `is_scrap=True` замість моделі `stock.scrap`.

# Списання зіпсованого тіста у цеху
move = self.env['stock.move'].create({
    'name': 'Списання зіпсованої сировини',
    'product_id': dough_product_id.id,
    'product_uom_qty': 15.5, # кг
    'product_uom': kg_uom_id.id,
    'location_id': kitchen_loc_id.id,
    'location_dest_id': scrap_loc_id.id,
    'is_scrap': True, # Ключовий прапорець Odoo 20!
    'store_by': 'lot', # Замість lot_id прапорців
})
move._action_done()

Карта впровадження Odoo 20 для «Вареники від Бабусі»

1

Оптимізація ліцензій та кадрів

180 працівників ліпки та пакування не заводити як користувачів у `hr.employee`. Замість цього створити кастомний модуль обліку робочих змін `bar.code.shift` без створення HR-профілів. Економія: €1,440/міс.

Контроль суворого дотримання рецептури вареників

3

Хвильовий відбір (Wave Picking) для морозильних камер

Налаштування нативного Wave Picking для пришвидшення роботи комірників у морозильних камерах (-18°C). Зменшення часу перебування персоналу на холоді за рахунок консолідованих хвиль відвантаження для автопарку.
